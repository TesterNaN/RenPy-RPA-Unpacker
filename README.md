# RenPy-RPA-Unpacker 🚀

> 不猜加密、不试密钥、不自己解析格式 —— **直接借用游戏自己的解包代码**。
> **不带参数运行就是一个中文交互向导**，那是这个工具的主要用法。

## 📋 项目简介

**RenPy-RPA-Unpacker** 是一个 Ren'Py 游戏 `.rpa` 存档解包工具。

**怎么用**：在终端里直接运行（不带参数），跟着中文向导回答几个问题就行——这是主要用法；
命令行参数是给脚本化、批处理准备的进阶用法，见下面的「命令行用法」。

它的最大特色是：**不重新实现 RPA 格式，而是把游戏自己的 `renpy/loader.py` 借来用。**

---

## ✨ 核心特色

### 🎯 最牛逼的点：用游戏自己的解密，而不是"猜"解密

很多解包器的思路是"识别加密算法 → 推导密钥 → 自己解密"。这条路注定要不停追新：
作者换个 XOR 常量、换个字段顺序、加个自定义 handler，工具就得更新一版。

本工具**换了个思路**：

- **不推导密钥** —— 解密函数是游戏自己带来的，密钥怎么来的也归它管
- **不识别算法** —— 加载器声明了什么格式，就按什么格式读
- **不需要配置** —— 没有"请选择加密方式"这一步，因为它压根不关心
- **格式自动跟进** —— 游戏换版本、作者换魔改方式，**工具代码一行都不用改**

这不是"更聪明的猜测"，是**从根上不猜**。

### 🚀 五个后端，一个原则

| 后端 | 一句话 | 适合什么时候 |
| --- | --- | --- |
| **静态 AST**（默认） | 把游戏 `loader.py` 里的解析代码**提取出来**，在自己进程里跑 | 一般情况。最快、不启动游戏、不写游戏目录 |
| **`--runtime`** | 用**游戏自带的 python** 起一次运行时，从外面调它自己的 `loader` | 静态后端读不出来，又不想写游戏目录 |
| **`--inject`** | 往 `game/` 放一个脚本，**让游戏自己解包**然后自动删掉 | 静态后端读不出来，且**没有文件完整性校验**（它会写 `game/`）。能力最强；也可以只放脚本、由你自己启动（`--inject-no-launch`）；脚本解包成功后**自我删除**，`--inject-cleanup` 只是没删掉时的兜底 |
| **`--env`** | 把 Ren'Py 扩展放进**用户级** `RENPY_SEARCHPATH` 指向的目录，**从商店/启动器启动**（或直接双击）该游戏即自动解包并退出 | 游戏目录一个字节不写，**完全绕过文件完整性/篡改检查**；可以由工具直接启动一次（`--env-launch`，**不改注册表、不用重启 Steam**），也可以等你从商店/启动器（或直接双击）启动。后者仅 Windows |
| **`--hook`** | 照玩家那样**启动游戏**，然后借它的线程在自己的解释器里跑 `load_from_archive` | 前四个全被构建本身否掉时：引擎编译成 `renpy.pyd`、没有启动脚本、`game/` 有清单校验、环境被净化。不写游戏目录、不猜格式；Windows + 64 位 + 8.4 代的动态 CPython |

**五个后端的共同点，也是整个工具唯一的铁律：以游戏自己的 loader 为准。**
所以"魔改游戏"不需要任何特殊处理——工具从来没打算比游戏更懂它自己的存档。

**`--env` 的机制**：把三个**用户级**变量（`RENPY_SEARCHPATH` 等）指向
`%LOCALAPPDATA%\renpy-unpack\searchpath`，并把一个 Ren'Py 扩展放在那里。之后**任何**启动游戏的方式
都会经过它：直接双击、快捷方式、商店或启动器（Steam / Epic / GOG Galaxy / itch.io / 独立启动器……）。

| 谁来启动 | 什么时候生效 |
| --- | --- |
| 直接双击、快捷方式、`--env-launch` | **立刻**。环境变量是进程启动时读的，新进程拿到的就是新值 |
| 一个**已经开着**的启动器 | 它会把**自己启动时**的环境快照传下去，所以看不到新值——重启这个启动器，或者干脆直接启动游戏 |

游戏解包后在窗口出现前自行退出，扩展随后**把变量还原**（原本设过的值还原成原值）并留下完成标记；
所以即使某个启动器还留着旧环境、你再启动一次，游戏也会正常玩。

`--wait` 等结果，`--unset-env` 手动收尾。实测 skyblue：1194/1194 与原后端逐字节一致，游戏目录
**零文件改动**。

### 💪 其他实在的功能


- **🖥️ 默认不写游戏目录** —— 静态后端、`--runtime`、`--env-launch` 全程只读，结果走管道返回。
  只有可选的 `--inject` 会临时放一个脚本进去，跑完（它自己）连 `.rpyc` 一起删。
  （顺带：写不进去也**从来不是死路**——`--runtime` / `--env-launch` 都不需要写权限。真正无解的
  组合只有 "没有 `loader.py` 源码**且**游戏起不来"，和只读无关。）
- **🔒 默认安全** —— 索引 pickle 默认用受限反序列化，恶意索引里的 `os.system` 会被拒绝
- **🛡️ 路径穿越防护** —— `../`、绝对路径、盘符、Windows 保留名一律拒绝
- **📦 无第三方依赖** —— 纯标准库，Python 3.9+，下载下来就能跑
- **⚡ 快** —— 1524 条目的存档 `--list` 约 **0.11 秒**（含解释器启动，实测三次
  108/110/118 ms）；同一个游戏 406.9 MB 全量解包约 **1 秒**
- **🧹 干净** —— `--inject` 跑完连 `.rpyc` 一起删，不留任何痕迹
- **🖥️ 纯标准库、不依赖平台特有接口**（Windows 上实测；Linux/macOS 的解释器探测路径
  代码里也处理了，但没实测过）

## 📦 命令行用法（跳过向导）

### 环境要求

**Python 3.9 或更高版本**（无第三方依赖，只用标准库）

### 安装

```bash
# 方式一：装成命令（推荐）
pipx install git+https://github.com/TesterNaN/RenPy-RPA-Unpacker

# 方式二：直接用，不安装
git clone https://github.com/TesterNaN/RenPy-RPA-Unpacker
cd RenPy-RPA-Unpacker
python unpacker.py --help
```

### 常用命令

```bash
# 1️⃣ 先看看存档里有什么（不写盘，最快）
renpy-unpack --game "D:\Games\SomeGame" --list

# 2️⃣ 一键解包（默认输出到 ./extracted/<游戏根目录名>/）
renpy-unpack --game "D:\Games\SomeGame" -j 16
```

**`--game` 指向游戏根目录**（含 `renpy/` 的那一层）。不带 `--game` 时，工具会从当前目录**自动向上查找**
——所以直接把 `unpacker.py` 丢进游戏目录双击也能跑。

### 三种等价写法

```bash
renpy-unpack --game "D:\Games\SomeGame" --list          # 装好后
python -m renpy_unpack --game "D:\Games\SomeGame" --list
python unpacker.py --game "D:\Games\SomeGame" --list
```

### 输出结果

解出来的文件放在 **`./extracted/<游戏根目录名>/`**（相对于你运行命令的目录），**完整保留原始目录结构**，
五个后端一致。选 `--env` 时 `-o` 是**基目录**，扩展会在它下面按**实际捕获到的**游戏建子目录。

**不要解到 `game/` 里面**：Ren'Py 会递归扫描 `game/`，多出一份脚本就会标签重复定义、游戏直接起不来。
工具发现输出落在那里时会警告。

### 什么时候用哪个后端

默认是静态 AST，够用就别换。拿不准就先 `--runtime --list` 看一眼。

| 情况 | 用哪个 |
| --- | --- |
| 一般游戏、游戏自带 `loader.py` | 默认（不加参数） |
| 解密在原生模块里 / 只有 `loader.pyc`，且**这个游戏没有文件完整性校验** | `--inject`（会写 `game/`，跑完自删） |
| 同上，但一点都不能碰游戏目录 | `--env-launch`（工具启动一次；不写游戏目录、不改系统设置） |
| 只能由商店/启动器启动（独占启动、DRM） | `--env`（装好后自己启动游戏；跑完自还原） |
| 游戏脚本加载不了（坏 mod、标签重复定义） | `--runtime` |
| 只想先看看有没有原生解密 | `--runtime --list` |
| **引擎被编译成 `renpy.pyd`、没有 `loader.py`，而且启动器有文件清单校验** | `--hook`（启动游戏，在它自己的解释器里跑；不碰磁盘） |

> 拿不准这游戏属于哪种构建，先跑 `--diagnose`：它会说清引擎形态、哪些归档是按内容认出来的、
> 以及每个后端能不能用、为什么。

> 唯一无解的组合是「**没有 `loader.py` 源码**（静态读不了）**且游戏起不来**（`--runtime` 起不来、
> `--inject` 也跑不动）」。**只读不在其中**：`--runtime`、`--env-launch` 和 `--hook` 都不写游戏目录，
> 写不进去只会让 `--inject` 退出选项，不会把你堵死。
>
> 走到 `--hook` 这一步（编译引擎 + 完整性校验）时，前四个后端会被构建本身否掉；
> 实测这种构建能破，做法是启动它、在进程内借它的线程跑一行 `load_from_archive`。

> `--inject` 和 `--runtime` **互斥**，同时给会直接报错让你选一个。
> `--inject` 也不能和 `--list` / `--dry-run` 同用——条目清单只存在于游戏进程内部。
> `--inject` 想自己启动游戏就用 `--inject-no-launch`（脚本解包成功后**会自己删掉**，
> 万一没删掉再用 `--inject-cleanup` 收尾）。


## 🔧 技术原理

### 五个后端分别在干什么

五个机制**互不相同，也不共享读取器代码**，唯一的共同点是终点——最后都落到游戏自己的 `load_from_archive()` 上：

| 后端 | 谁执行 loader 代码 | 谁提供运行上下文 | **我们的代码怎么进去** | 解密函数从哪来 |
| --- | --- | --- | --- | --- |
| **静态 AST** | **我们的**解释器（本进程） | 我们的替身（`renpy`/`RWopsIO`/`loads`） | **不进游戏**：源码 → AST → 重新生成 → 执行 | 从游戏 `loader.py` 提取出来的**那份源码** |
| **`--runtime`** | 游戏解释器（**子进程**） | 游戏自己 | **不进游戏**：探针经 `-c` 传进去，结果走管道回来 | `import` 到的**活对象** |
| **`--inject`** | 游戏解释器（**游戏本体**） | 游戏自己 | 往 `game/` 放一个 `.rpy`，跑完**自己删掉** | `import` 到的**活对象** |
| **`--env`** | 游戏解释器（**游戏本体**） | 游戏自己 | 扩展放在我们的目录，挂到 `RENPY_SEARCHPATH`（Ren'Py 自己的 `.rpe.py` 机制） | `import` 到的**活对象** |
| **`--hook`** | 游戏解释器（**游戏本体**） | 游戏自己 | **改它进程里的一个导入槽**，让引擎自己那次调用跳到我们的 stub（跑完还原并尾跳原函数） | `import` 到的**活对象** |

一句话概括：**静态 AST 是"抄一份带回家"，`--runtime` 是"打个电话问"，`--inject` 是"往它家里塞张
纸条"，`--env` 是"在它家门口贴张告示"，`--hook` 是"站在它身后握着它的手写"。**

### 静态后端：AST 提取而不是字符串切割

早期版本用 `str.find()` 按偏移切函数，结果切出过半截函数
（`content.find('break', start2)` 匹配到了函数体中间的 `break`）。现在：

1. `ast.parse()` 解析 `loader.py`
2. 按**名字**找到 `RPAv1/v2/v3ArchiveHandler`、`index_archives`、`load_from_archive` 等，
   **保留原始 AST 节点**（装饰器、`self` 风格原样保留，自动适配不同 Ren'Py 版本）
3. 遍历这些定义引用的名字，算出**依赖闭包**
4. 把无法从源码得到的少数名字（`RWopsIO`、`loads`、`renpy`）用替身补上，并按需裁剪
5. `ast.unparse()` 输出一个自包含模块

结果是「结构上必然正确」，而不是「碰巧正确」。
测试 `test_extracted_definitions_match_loader_exactly` 会把提取结果和原文件**逐个节点比对**，
防止将来悄悄退化。

### `--runtime`：在游戏脚本加载之前抢回控制权

```
renpy.bootstrap.bootstrap()      ← 探针从这里进去
  └ renpy.import_all()           ← renpy.loader 在这里进 sys.modules  ← 探针在这一刻停下
  └ renpy.main.main()            ← 真正的脚本加载在这里
```

探针用 `sys.settrace` 盯着 `renpy.loader` 进入 `sys.modules` 的那一瞬间，立刻把控制权抢回来。
**实测证据**：LoveYuri 自己都启动不了（`game/extracted/` 和 `game/rpy/` 重复定义 `gui.rpy`），
但 `--runtime` 对它 **exit=0、1524 条目**。游戏能不能玩，完全不影响读它的存档。

### `--inject`：让游戏自己跑

```
renpy.loader.index_files()          main.py:367   ← 索引已建好
renpy.game.script.load_script()     main.py:412   ← init python early 在这里执行
renpy.display.core.Interface()      main.py:572   ← 到这一步才会开窗口
```

脚本在第二行和第三行**之间**就 `os._exit(0)` 退出了，所以**窗口根本不会被创建**。
它只做三件事：遍历现成的索引、调 `load_from_archive()`、写盘——**完全不解析存档格式**。

### `--env`：挂到 Ren'Py 自己的扩展点上

前三个后端都要求"我们能碰到那个进程"：静态读源码、`--runtime` 起子进程、`--inject` 往 `game/` 放脚本。
`--env` 换了个方向——**让 Ren'Py 自己来找我们**：

```
RENPY_SEARCHPATH=<我们的目录>            ← 用户级环境变量，renpy/loader.py 启动时读
  └ Ren'Py 把这个目录并进 searchpath
      └ 启动早期：执行搜索路径下的 *.rpe.py     ← 我们的扩展在这里跑
          └ renpy.loader.index_files() 已经把索引建好了
              └ 扩展遍历 loader.archives → load_from_archive() → 写盘 → 还原环境 → os._exit(0)
```

- **游戏目录一个字节都不写**：`RENPY_SEARCHPATH` 和 `*.rpe.py` 都是 Ren'Py 自己的机制，我们只是把文件
  放在它一定会看的地方。
- **扩展自己收尾**：解密完把三个变量**还原**——只碰自己设过的、且值没被别人改过的那些（原本存在的值
  还原成原值，本不存在的删掉），留一个 `spent` 标记让整件事只发生一次，然后 `os._exit(0)`，
  在窗口出现之前就退出。
- **`--env-launch` 是它的即用形态**：工具自己启动游戏，三个变量只塞进那一个子进程，**完全不碰注册表**，
  所以也不限平台；只有"等你启动"那一种（`--env`）才需要写用户级变量，而那一层在 Windows 上是注册表。

**实测**（skyblue，`--env-launch`）：1194/1194 与其它后端逐字节一致、游戏目录**零改动**、游戏 2.7 秒后
自行退出、事后扩展已撤、三个用户级变量前后都是"未设置"。

### `--hook`：在引擎自己的进程里做

**面向谁**：Ren'Py **8.4 及以后**（这一代把 CPython 动态链接成 `libpython3.X.dll`），以及任何把引擎编译成 `renpy.pyd` 的发行版。8.3 及更早的构建不在范围内——它们把 CPython 静态链进 `librenpython.dll`，导入表里根本没有这些调用，钩不上；不过那一代的游戏是源码发行，前四个后端覆盖得到（见 `docs/NOTES.md` 的实测记录）。

前四个后端都在问文件系统：有没有 `loader.py`、有没有启动脚本、有没有 `renpy.py`。一个把引擎编译成
`renpy.pyd`、再给 `game/` 加文件清单校验的发行版，**一次性把四个答案都删掉了**：

| 前端 | 这个构建为什么挡住它 |
| --- | --- |
| 静态 AST | 没有 `renpy/loader.py`，格式只存在于编译后的引擎里 |
| `--runtime` | 没有 `<Game>.py`，引擎由 exe 自己启动 |
| `--inject` | `game/` 多一个文件就拒绝启动（实测 exit 10） |
| `--env` / `--env-launch` | 没有 `renpy.py`，且启动器净化 `RENPY_*` / `PYTHON*` |

`--hook` 换个思路：**照玩家那样把游戏启动起来**，然后借它的线程跑一行解包代码。步骤都不依赖具体游戏：

1. 按玩家方式启动 exe（顺带补上 Steam 的 `SteamAppId` / `SteamClientLaunch` / `SteamPath`——缺了它会
   exit 53）；
2. 找到加载了 `libpython3.X.dll` 的进程；
3. 在游戏目录里找**谁从 CPython 导入符号**（`renpy.pyd`、`librenpython.dll` 或某个 `.pyd`）；
4. 把一小段 stub 写进**已加载镜像的零区**——这种进程通常开着 ACG（禁止新的可执行内存），但镜像页
   允许改成可写可执行；
5. 把该模块的一个导入槽指向 stub；stub 先把槽位改回原值，再调 `PyRun_SimpleString` 跑 payload，
   最后尾跳到原函数——所以引擎自己的那次调用照常发生；
6. payload 在引擎的 Python 线程上、持着 GIL 运行，调用的是 **`renpy.loader.load_from_archive()`**：
   解密算法一行都没写。

**实测**（同一份代码，只换游戏路径）：

| 游戏 | 构建 | 结果 |
| --- | --- | --- |
| HuangmeiC | 编译引擎 `renpy.pyd` + 文件清单校验 | 7019 个成员 / 2610.0 MiB / 0 失败，6870 个魔数校验 0 错 |
| 黄莓C Demo | 源码 8.5 | 1447/1447 与 AST 逐字节一致 |
| Dream_of_BluePlanet | 源码 + `ILOVEYOU0000` + 索引字段换序 | 2971/2971 一致 |
| 小小的身影 | 源码 + RPAE-2.0 | 2003/2003 一致 |
| LOVE YURI | 源码（嵌套目录） | 1524/1524 一致 |

**限制**（都是实测，不是推测）：

- 只支持 Windows；它改的是别的进程的导入表，某些杀软会把这种行为叫做注入——它就是注入；
- **只支持 64 位构建，32 位不做**。原因见下面的小节；遇到 32 位目标时它会在写任何内存之前拒绝，
  并说明原因，而不是把游戏搞崩；
- 8.3 及更早的 `librenpython.dll` 把 CPython 静态链在体内，不走导入表，这套钩不上（不过那些构建是
  源码发行，前四个后端覆盖得到）；
- 有的启动器必须拿到 Steam AppID，`--steam-appid` 可以显式给。

#### 为什么不做 32 位

Ren'Py 8.x 的 Windows 发行目录是 `lib/py3-windows-x86_64/`（本项目实测的 6 个游戏全是这样），32 位
只出现在 7.x 时代；而 7.x 是 Python 2.7，payload 本来就要另写一版。更实际的是：现在的 Windows 客户端
几乎都是 64 位，发行方没有理由再去产出 32 位构建。

即便真遇到 32 位构建，也不是"改几个字节"就行——注入的 stub 是 x64 机器码（`48` 前缀在 32 位下是
`dec eax`、`41` 是 `inc ecx`、没有 R8/R9），调用约定不同（x64 走 RCX/RDX/R8/R9 + 32 字节影子空间，
x86 走栈传参且 `cdecl` 由调用方清栈），IAT 槽位是 4 字节而我们会写 8 字节（会覆盖相邻槽位），
注入方本身也得换成 32 位进程（64 位对 32 位 `CreateRemoteThread` 要求起始地址落在对方 4 GB 内）。
要支持就得另写一份 x86 stub 加一个 32 位注入器，还得找一个 32 位样本做回归——没有样本时写这种代码
就是猜，所以这里选择明确拒绝。

### 顺带修了 Ren'Py 自己的一个 bug 🐛

RPAv3 支持把一个文件拆成两段，而 Ren'Py 8.5.2 的 `load_from_archive`
**构造好读取器之后把它丢了**：

```python
rv = RWopsIO.from_split(a, b, name=name)
rv = io.BufferedReader(rv)      # <-- 没有 return
```

于是掉出循环 `return None`，一个索引里写得清清楚楚、明明存在的文件看起来"不存在"。
本工具的 `Reader.load()` 补上了这一步。

## ❓ 常见问题

### Q: 为什么不用自己写的解密？为什么非要读游戏的文件？

A: 因为**格式的权威是游戏自己**。同一个 `.rpa` 扩展名，官方 SDK 认为是
`RPA-3.0 ` 魔数，而某个真实游戏改成了 `.dll` + `ILOVEYOU`。
拿标准实现去读，报出来的会是"找不到存档"——**而 1.5 GB 的存档就躺在那里**
（实测：那个游戏 `game/` 里的五个"系统 DLL"分别是 558.7 / 434.0 / 369.1 / 215.3 / 1.5 MB）。
自己写一套解密，就是在和游戏的作者玩一场永远追不上的追逐战。

### Q: 工具需要放在游戏根目录吗？

A: 不需要。用 `--game` 指定即可；不带 `--game` 时会从当前目录**自动向上查找**。
放在游戏根目录直接跑当然也可以。

### Q: 提示"没有找到任何存档"

A: 依次检查：
- `--game` 指向的是不是游戏**根目录**（含 `renpy/` 的那一层）
- 游戏是不是**已经完全解包**了（资源是散装文件，那就没东西可解）
- 存档的扩展名是不是被改过（比如伪装成 `.dll`）——本工具会自动按 loader 声明的扩展名去找
- 加 `--runtime --list` 看看游戏自己的运行时能认出几个存档

### Q: 解包失败怎么办？

A: 按这个顺序试：

| 报的错 | 含义 | 换哪个 |
| --- | --- | --- |
| `could not find this game's own renpy/loader.py` | 游戏只发了 `loader.pyc` | `--inject` 或 `--runtime` |
| `cannot write into ...` | `game/` 写不进去 | `--runtime` |
| `could not take control of the game's runtime` | 运行时没能抢到控制权 | `--inject` |
| `the game started but never ran the injected script` | 游戏脚本加载失败（坏 mod？） | `--runtime` |

**三条路机制完全独立，一条失败不代表另一条也失败。**

### Q: 支持哪些 Ren'Py 版本？

A: 支持**按 loader 自己的说法**来读——这比"支持某个版本列表"更靠谱。具体分两层说清楚：

**第一层：存档格式。** 不自己实现 RPA，所以格式怎么改都能读。真实游戏上实测成功的有：
标准 `RPA-3.0`、XOR 混淆索引、偏移整体平移与假偏移、伪装成 `.dll` / `.blend` 的扩展名
与自定义魔数（`ILOVEYOU`、`WJZ-4.9 `）、索引字段顺序互换、配套 `.zip` 存数据、
自定义 handler、只有 `loader.pyc` 的发行版、完全没有存档的散装游戏。

**第二层：loader 的结构。** 静态后端要"替游戏把 loader 驱动起来"，所以必须知道它的结构。
而结构是**上游 SDK 规定的**（不是游戏作者改的），所以是可枚举的。实测上游已发布版本，
**只有两种形状，分界线在 8.4**：

| | `arc_files` | `archive_handlers` | `index_archives()` | `renpy.compat` 导入 `unicode` |
| --- | --- | --- | --- | --- |
| **8.4 及以后**（8.4.x / 8.5.x / 8.6 nightly） | 有 | `ArchiveHandlers` 对象 | `archives.clear()` | 否 |
| **8.3 及以前**（7.8.x / 8.0.x – 8.3.x） | 无 | 普通 list | `archives = []` 重新绑定 | 是 |

两种形状**都支持**，而且是按能力探测的（`getattr` / `hasattr`），不是按版本号分支——
将来上游再换形状，代码不会因为版本号不认识就拒绝工作。逐列的依据和内部分歧见
[docs/NOTES.md 的「上游矩阵」](docs/NOTES.md#上游矩阵支持哪些-renpy-版本)。

- **实测解包成功**：Ren'Py **8.3.4**、**8.5.2**、**8.6.0 nightly**。
- **合成存档端到端回归覆盖**：RPAv1 / RPAv2 / 分段存档 / Python 2 pickle。
- **例外**：RPAv1（`.rpi`）目前只能**列清单**，成员数据的落点没有实测样本，
  没有冒险实现——欢迎提供样本。

### Q: 会往我的游戏目录里写东西吗？

A: **默认不会。** 静态后端和 `--runtime` 全程不写游戏目录。
`--inject` 需要往 `game/` 放一个脚本，跑完会**连 `.rpyc` 一起删掉**——
`.rpyc` 留在那里会让游戏每次启动都重跑一遍解包，这是个真实的坑。

### Q: 解包出来的文件放在哪？

A: 默认 `<游戏根>/extracted_files/`，可以用 `-o` 改。
默认**不放在 `game/` 里面**是故意的：Ren'Py 会递归扫描 `game/`，
把 `.rpy` 解包进去会让它重复定义同一个标签，游戏直接启动不了。

```
renpy_unpack/
    core.py                  # 发现游戏、构建读取器、并行提取、CLI、后端调度
    classify.py              # 按证据判断构建形态、哪些后端可用（--diagnose）
    hook.py                  # 第五后端：在游戏进程内跑（--hook）
    ast_extract.py           # 静态后端：AST 提取核心
    runtime.py               # 活运行时后端：探测解释器/启动器、流式协议
    probe.py                 # 活运行时后端：在游戏进程里跑的探针
    inject.py                # 自解包后端：生成脚本、跑一次游戏、读清单、清理
    _inject_body.py          # 注入脚本的正文模板

docs/NOTES.md                # 开发笔记：原理、实测数据、踩过的坑
tests/                       # 151 个用例，无第三方依赖
```
